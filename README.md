# avito_parser_views

Сбор просмотров с Авито по артикулам запчастей. Ходит не браузером, а обычными запросами:
всю грязную работу — отпечаток TLS, барьеры, капчу, разбор страниц — делает библиотека
[avito](https://github.com/Stepan2222000/avito_library). Здесь живёт то, чего в ней нет:
очереди задач, поставщик адресов и порядок обхода.

Работа идёт в две ступени. Сначала по артикулу забирается выдача каталога — так находятся
объявления. Потом по каждому объявлению забирается карточка: просмотры есть только в ней,
в выдаче их нет вообще. Наблюдения складываются в базу библиотеки на каждый визит, поэтому
динамика просмотров получается сама, без отдельной таблицы.

Проект собирается по этапам: сначала договариваемся об алгоритме, потом он появляется в
коде. Сделаны все четыре: очередь артикулов, обход выдачи, разбор карточек с просмотрами и
недельный переобход.

## Раскладка

| база | порт | зачем |
| --- | --- | --- |
| `smart` | 5402 | источник артикулов, только чтение |
| `avito_data` | 5424 | объявления, продавцы, наблюдения, находки по запросам — пишет библиотека |
| `avito_parser_views` | 5427 | только очереди: что предстоит обойти и что уже обошли |

Собранного у себя мы не держим совсем. Просмотры лежат в наблюдениях библиотеки, а связь
артикула с объявлениями она тоже ведёт сама: на каждый артикул создаётся запрос с ключом
`/all/zapchasti_i_aksessuary?q=<артикул>`, а найденное складывается в находки — с номером
страницы и датами первой и последней встречи.

## Установка

```bash
git clone https://github.com/Stepan2222000/avito_parser_views.git
cd avito_parser_views
git clone --depth 1 https://github.com/Stepan2222000/avito_library.git lib/avito_library
pip install -r requirements.txt

cp .env.example .env          # адреса баз, список прокси, темп обхода
cp где-то/proxies.txt .       # список адресов, в репозитории его нет
python -m avito_views init    # применить схемы: нашу и библиотечную
```

## Что уже работает

```bash
python -m avito_views load             # залить артикулы из smart в очередь
python -m avito_views run              # обход: карточки, а в промежутках выдачи
python -m avito_views refresh          # снять просмотры заново по давним карточкам
python -m avito_views status           # что сейчас в очередях
python -m avito_views proxies          # состояние пула адресов
python -m avito_views reset            # вернуть в очередь брошенные задачи
```

`load` приводит очередь в соответствие с источником: добавляет новые артикулы и удаляет
задачи на те, которых в `smart` больше нет. Собранное по удалённым остаётся в базе
библиотеки. Флаг `--again` возвращает в очередь и уже обойдённые артикулы.

`run` делает всю работу одними и теми же воркерами. Карточки в приоритете: воркер берёт
выдачу только тогда, когда разбирать нечего. Из этого следует, что просмотры начинают
копиться с первых минут, а полная карта объявлений собирается последней. Сами объявления,
продавцов, фотографии, наблюдения за просмотрами и связь с артикулом пишет библиотека в
свою базу; у нас остаётся только ход работы.

## Как обходится выдача

Первая страница даёт число страниц, дальше берём по одной. Просить страницу, которой нет,
нельзя — задача падает целиком, а число страниц Авито ещё и завышает: обещанная страница
может не открыться, и тогда это считается концом выдачи, а не поломкой. Останавливаемся
также на неполной странице: меньше пятидесяти объявлений значит последняя.

Листаем по дате. Выдача во время обхода сдвигается, и при сортировке по дате новые
объявления толкают её вниз — получаются повторы, а не пропуски; повторы бесплатны, номера
всё равно дедуплицируются. Сортировку библиотека проверяет по пагинатору и роняет задачу,
если Авито её выбросил, так что «листали не то, что думали» не случится молча. Отключается
пустым значением `SORT`.

Итог артикула — один из трёх статусов. «Готова» с числами: сколько нашлось по мнению
Авито, сколько страниц, сколько собрали. «Пусто» — по номеру нет объявлений: Авито трижды
с разных адресов отдал страницу подбора по артикулу вместо выдачи. «Ошибка» — три
неудачные попытки; страница, на которой сломалось, сохраняется в `dumps/`.

Воркеров по умолчанию сорок при ста адресах, и это не жадность, а замер: один воркер
держит адрес, пока тот не получит блок, поэтому запас нужен. Семьдесят воркеров дают
меньше сорока — начинается ожидание свободного адреса.

## Как разбираются карточки

Просмотры есть только в карточке, поэтому по каждому найденному объявлению мы идём на
`/items/<номер>` — по одному номеру за вызов, потому что библиотека роняет всю задачу на
первом же снятом объявлении. Наблюдение с просмотрами и ценой она пишет на каждый визит,
так что динамика получается сама.

Снятое объявление помечается снятым и больше не запрашивается — но если оно снова
появилось в выдаче по артикулу, значит живо, и мы возвращаем его в очередь. Карточка, три
раза пришедшая без данных, получает «ошибку» окончательно: её страница лежит в `dumps/`,
и дальше это разбирается руками, а не повторами. В замере таких было одна на три тысячи.

## Переобход

`refresh --days 7` возвращает в очередь карточки, которых не касались неделю, и обходит их
заново — в наблюдениях появляется новая точка, и по ней видно, насколько выросли просмотры.
Берутся только успешно разобранные: снятые оживают лишь через выдачу, а «ошибка»
окончательна.

Новые объявления по уже обойдённым артикулам ищет `load --again`: она возвращает артикулы в
очередь, и обход проходит по ним заново. Отдельной команды для этого нет — это то же самое
действие.

## Как выбираются артикулы

Номер сначала чистится от дефисов и прочих знаков, а потом отбрасывается, если в нём
меньше пяти символов или если это только цифры и их не больше шести. Причина не в
аккуратности, а в замерах: по `0810` Авито находит 8334 объявления, по `12224` — 855, по
`09-812` — 1900, а по настоящему номеру `8M0111544` — пять. Короткое число Авито понимает
как просто число и отдаёт всё, где оно встречается, причём дефисы для него ничего не
значат. Из 4322 артикулов остаётся 3682.

Обходить нужно все, а не по одному на деталь: у половины деталей есть артикулы-аналоги, и
замер показал, что самый длинный из них приносит только 42% объявлений детали, каждый
следующий добавляет ещё 18%, а по одному артикулу на деталь собралось бы всего 24%.

## Что уже известно про Авито и адреса

Замеры сделаны вживую, на пуле из ста адресов ProxyElite.

Разбирается только страница вида «город или `/all` + категория + `?q=`». Лендинг категории
и сквозной поиск `/all?q=` библиотека не понимает — это другие типы страниц. Просить
страницу, которой нет, нельзя: задача падает целиком, а число страниц Авито ещё и
завышает.

Скорость упирается в адреса, а не в число воркеров. Адрес работает около 18 минут, потом
получает получасовой блок, поэтому одновременно годна примерно треть пула. На отдохнувшем
пуле выходит 900 страниц в минуту, установившийся темп — около 300. Сорок воркеров дают
больше, чем семьдесят: с семьюдесятью начинается ожидание свободного адреса.

Через домены на 8443 по схеме `https` отвечают все сто адресов, а те же адреса по `http`
на 8080 четвертью не открываются вовсе.

Адрес принадлежит одному воркеру, пока живёт. Исходы от библиотеки: «прошло» — адрес
свободен сразу; «молчит» — минута отдыха, а после пяти обрывов подряд адрес выводится из
пула как нерабочий; блок — четверть часа отдыха, дальше проба каждые пять минут. Отдых не
растёт: замер показал, что растущий отдых за полчаса работы выел пул и уронил темп втрое.
Состояние адресов живёт в памяти процесса, поэтому перезапуск начинается с холостых проб —
это одна страница на адрес и того не стоит, чтобы держать таблицу.

## Чего здесь нет

Отчётов. Просмотры версионируются в наблюдениях библиотеки, а как их читать — решается
запросами к базе, когда понадобится. Автозапуска по расписанию тоже нет: таймер поставим,
когда первый полный проход покажет своё время.
