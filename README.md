# avito_parser_views

Сбор просмотров с Авито по артикулам запчастей. Ходит не браузером, а обычными запросами:
всю грязную работу — отпечаток TLS, барьеры, капчу, разбор страниц — делает библиотека
[avito](https://github.com/Stepan2222000/avito_library). Здесь живёт то, чего в ней нет:
очереди задач, поставщик адресов и порядок обхода.

Работа идёт в две ступени. Сначала по артикулу забирается выдача каталога — так находятся
объявления. Потом по каждому объявлению забирается карточка: просмотры есть только в ней,
в выдаче их нет вообще. Наблюдения складываются в базу библиотеки на каждый визит, поэтому
динамика просмотров получается сама, без отдельной таблицы.

## Раскладка

Три базы, каждая при своём деле:

| база | порт | зачем |
| --- | --- | --- |
| `smart` | 5402 | источник артикулов, только чтение |
| `avito_data` | 5424 | объявления, продавцы, наблюдения, находки по запросам — пишет библиотека |
| `avito_parser_views` | 5427 | только очереди: что предстоит обойти и что уже обошли |

Собранного у себя мы не держим совсем. Просмотры лежат в наблюдениях библиотеки, а связь
артикула с объявлениями она тоже ведёт сама: на каждый артикул создаётся запрос с ключом
`/all/zapchasti_i_aksessuary?q=<артикул>`, а найденное складывается в находки — с номером
страницы и датами первой и последней встречи. Поэтому в нашей базе остаётся только ход
работы: статус, попытки, когда взяли, когда спарсили.

Для отчётов команда `init` заводит в `avito_data` две вьюхи: `артикулы_объявления`
(артикул достаётся из ключа запроса) и `просмотры_по_артикулам` — артикул, день, сколько
объявлений и сколько у них просмотров. За день берётся последнее наблюдение по каждому
объявлению, иначе повторные визиты считались бы дважды.

## Установка

```bash
git clone https://github.com/Stepan2222000/avito_parser_views.git
cd avito_parser_views
git clone --depth 1 https://github.com/Stepan2222000/avito_library.git lib/avito_library
pip install -r requirements.txt

cp .env.example .env          # адреса баз и путь к списку прокси
cp где-то/proxies.txt .       # список адресов, в репозитории его нет

python -m avito_views init    # применить схемы (библиотечную и нашу) и вьюхи для отчётов
```

## Работа

```bash
python -m avito_views load            # залить артикулы из smart в очередь
python -m avito_views run             # обход: каталоги и карточки вперемешку
python -m avito_views status          # что в очередях и что собрано

python -m avito_views refresh --days 7   # переобойти карточки, которых давно не касались
python -m avito_views catalogs           # пустить каталоги заново и добрать новые объявления
python -m avito_views proxies            # состояние пула адресов прямо сейчас
python -m avito_views reset               # вернуть в очередь брошенные задачи
```

Обычный ритм: `refresh` раз в неделю даёт свежие просмотры по уже известным объявлениям,
`catalogs` запускается отдельно, когда нужно найти новые объявления — найденные карточки
он парсит тем же прогоном.

## Как выбираются артикулы

Из `part_articles` берутся все артикулы, кроме заведомо мусорных: короче пяти знаков и
чисто числовых до шести знаков. Причина не в аккуратности, а в замерах: по `0810` Авито
находит 8334 объявления, по `12224` — 855, а по настоящему номеру `8M0111544` — пять.
Короткое число Авито понимает как просто число и отдаёт всё, где оно встречается. Из 4322
артикулов после отсева остаётся 3702, они покрывают 1651 деталь из 1859.

Путь поиска — `/all/zapchasti_i_aksessuary?q=<артикул>`: `/all` это вся Россия. Категорию
приходится называть явно, потому что сквозной поиск `/all?q=` библиотека не разбирает —
это другой тип страницы. Лендинг категории (`/rossiya/zapchasti_i_aksessuary`) она тоже не
разбирает, только выдачу.

## Как устроен обход

Воркеры одинаковые: каждый берёт из очереди задачу любого вида. Пока карточек в очереди
меньше порога (`CARDS_THRESHOLD`), разбираются артикулы; как только накопилось — воркеры
переключаются на карточки. Поэтому очередь держится около порога, а не распухает на
несколько тысяч задач, и оба вида работы идут вперемешку.

Один воркер — один адрес, пока тот жив: библиотека возвращает адрес только когда с ним не
сложилось. Значит воркеров должно быть меньше, чем адресов, иначе замены не найдётся и
пул встанет в ожидание. Это проверено: сто воркеров на сто адресов выгорают за секунды и
дальше ждут остывания.

Страницы выдачи берутся по одной. Просить страницу, которой нет, нельзя — задача падает
целиком, а сколько их всего, известно только с первой страницы.

## Сколько это занимает

Замерено на живом прогоне: 40 воркеров дают устойчивые **860–900 карточек в минуту**, и
после первой минуты адреса перестают выбывать вовсе — отсеиваются только те, что были
заблокированы заранее. Семьдесят воркеров дают меньше (около 700 в минуту) и заставляют
ждать свободных адресов: узкое место не в воркерах, а в пуле, поэтому запас нужен.

По тысяче обойдённых артикулов: 18 объявлений на артикул в среднем, а одно объявление
находится по двум артикулам-аналогам. На все 3702 артикула это порядка 65 тысяч
объявлений, то есть полный проход по карточкам — чуть больше часа.

## Что роняет задачу, а что нет

Барьеры, капча, смена адреса и обрывы — это обычная работа библиотеки, наружу они не
выходят. Задачу роняет непонятная страница, сбой разбора или снятое объявление. Упавшая
задача возвращается в очередь и после трёх попыток помечается ошибкой; обход при этом
продолжается на других задачах. Снятое объявление помечается мёртвым в базе библиотеки и
больше не запрашивается.

Если выдача по артикулу упирается в потолок Авито (сотая страница, около пяти тысяч
объявлений), артикул помечается признаком `wide` — значит часть объявлений недоступна и
запрос надо сужать.

Отдельный случай — статус `пусто`. По части номеров Авито отдаёт страницу подбора по
артикулу: разметка есть, данных нет, и никакой выдачи из неё не достать. Проверено, что по
этим же номерам широкая категория «Транспорт» отвечает «ноль», а запрос с пробелом внутри
номера находит совсем другие детали, поэтому обходного пути нет. Такой артикул получает
статус `пусто` — но только после трёх попыток с разных адресов, чтобы разовый сбой не
превратился в тихий ноль. На тысяче артикулов таких оказалось 52, то есть около пяти
процентов.

Известное ограничение: примерно у одной карточки из трёх тысяч страница объявления
приходит без данных, и библиотека её не опознаёт. Такая задача после трёх попыток
получает статус `ошибка` и остаётся видна в сводке. Страницы, на которых задача сломалась
окончательно, складываются в `dumps/` — по ним потом и разбираемся.

## Что известно про адреса

Замеры на нашем пуле ProxyElite (сто адресов):

* через домены на 8443 по схеме `https` соединение открывают все сто, а те же адреса по
  `http` на 8080 четвертью не отвечают вовсе;
* блок после 403 держится около получаса, но часть адресов свободна уже через пятнадцать
  минут, и пробы блокировку не продлевают — поэтому первая проба ранняя, а отдых растёт
  только если адрес всё ещё в блоке;
* капча и получасовой таймер — разные вещи: капчу библиотека решает сама и адрес при этом
  остаётся в работе.
